## What is now integrated

1. Plain-language Anna intake and contextual risk review remain advisory. The deterministic Verigate engine remains the final authority.
2. The first check remains a non-persistent preview. It reads persisted state for rolling limits but does not create a history record.
3. A separate, explicit Anna UI confirmation triggers a fresh, persistent capability-bound authorization request. The exact confirmation event is included in the signed payment intent.
4. The Anna Executa creates or resolves a policy-scoped payment capability and invokes the existing GuardrailEngine.authorize_with_capability path.
5. The authorization path persists the attempt and issues an Ed25519 one-time ExecutionAuthorization only for a fresh ALLOW. WARN and BLOCK receive no execution authority.
6. Anna verifies the Decision Receipt and the Execution Authorization before displaying either.
7. Existing ExecutionRouter remains the execution boundary. Tests prove that it invokes an executor callback only once, rejects replay, and rejects action tampering before the callback.

## Policy controls restored

- Per-transaction USDC cap: 500
- First-payment USDC cap: 50 (WARN when exceeded)
- Human-review threshold: 250 USDC
- Rolling 24-hour spend cap: 2,000 USDC (WARN when exceeded)
- Rate limit: 30 recorded payment attempts per minute (BLOCK when exceeded)
- Allowed networks: Base, Ethereum, Solana
- Allowed asset: USDC
- Network-specific recipient address validation and positive-amount validation remain enabled.

The preview reads current audit history to evaluate stateful limits. The separate authorization step records the new attempt, so later decisions see that event. BLOCK attempts do not count toward spend; the rate limiter tracks recorded attempts according to the existing Verigate storage rules.

## Security and execution boundaries

- Anna does not access wallet private keys, sign wallet transactions, or broadcast funds.
- A permission is an authorization artifact, not proof of transaction submission.
- A downstream wallet/executor must bind its actual transaction to the exact authorized payment action and route it through ExecutionRouter.
- The core Verigate EVM and Solana adapters/RPC clients exist in the repository; they are not yet connected as a wallet adapter inside the Anna app.
- An executor that calls a wallet directly and bypasses ExecutionRouter is not protected by this Anna integration.
- ALLOW means the request is within the configured policy. It does not establish that a recipient is trustworthy or guarantee chain execution.
