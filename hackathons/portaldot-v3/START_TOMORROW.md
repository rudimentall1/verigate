### D. Contract shape: one operation, not a generic call relay

Implement a demo treasury that authorizes one operation: transfer a fixed demo token to a recipient for a specific amount. Keep the demo token address fixed at deployment. Do not expose an unrestricted caller-selected `target.call`.

The action authorization should include the exact recipient, token/operation, amount, intent or action digest, nonce and deadline. The EIP-712 domain must bind `chainId` and `verifyingContract`. The contract must:
- accept only the configured EIP-712 signer;
- reject an expired deadline;
- reject a used nonce;
- reject invalid recipient/amount;
- bind the signature to the exact action parameters;
- transfer only the configured demo token;
- emit an event with the intent/action digest and operation fields.

Do not pass Verigate's Ed25519 signature to Solidity and assume it can verify it. The bridge must first verify the actual Verigate Ed25519 execution authorization off-chain using the trusted Verigate public key and verify that its action, policy outcome, target, token, amount and PortalDot network match. Only then may it create a narrowly scoped EIP-712 authorization. Document the bridge key as a trust boundary.

A blocked or invalid action must not receive a bridge signature. Tests should assert there is no transaction broadcast, not merely that the UI displays BLOCK.

### E. Integration with existing Verigate

Reference files in the Verigate checkout:
- `api/main.py`, `api/schemas.py`: `POST /v1/actions/authorize` is the generic action-authorization interface.
- `core/models.py`: canonical `ActionIntent` fields and context digest.
- `core/identity.py`: agent-signed action intent.
- `core/capabilities.py`: scope and revocation checks.
- `core/policy.py`, `policies/default.yaml`: deterministic constraints.
- `attest/receipt.py`: signed execution authorization format and verifier.
- `enforcement/evm_rpc.py`, `enforcement/chain_verification.py`: RPC and receipt evidence patterns.
- `docs/threat-model.md`: relevant trust boundaries and known gaps.

The root repository is not packaged as a normal `verigate` pip package. Do not write `pip install verigate` into instructions unless that distribution path is actually created and tested. For fastest integration, run Verigate from its existing checkout as a local service with API authentication configured, or write a minimal documented adapter against the checked-out Python module path. The bridge must not infer that an HTTP status code alone grants authority; it must validate the signature and fields.

## Test matrix required before calling it an MVP

### Contract unit tests (local EVM)
- [ ] Valid signature and exact action succeeds.
- [ ] Wrong signer fails.
- [ ] Recipient mutation fails.
- [ ] Amount mutation fails.
- [ ] Token/operation mutation fails.
- [ ] Wrong chain/domain fails.
- [ ] Wrong verifying contract/domain fails.
- [ ] Expired signature fails.
- [ ] Replayed nonce fails.
- [ ] Zero recipient and zero/invalid amount fail.
- [ ] Transfer amount and event exactly match the signed action.

### Verigate bridge and end-to-end tests
- [ ] Verigate ALLOW + valid signed action produces one EIP-712 authorization.
- [ ] BLOCK/WARN produces no EIP-712 authorization.
- [ ] Altered Ed25519 authorization is rejected.
- [ ] Altered intent/action is rejected before signing.
- [ ] Wrong target/network/token/amount is rejected.
- [ ] The test captures broadcast count and proves denied actions have zero broadcasts.
- [ ] Successful testnet transaction is independently read back; chain ID and receipt are checked.
