# Details — paste into the public Build description

## AI can prepare the payment. It must not be able to authorize itself.

An AI agent that can move money creates a new security problem: a wrong recipient, an altered amount, a replayed approval, or a prompt-injected instruction can become a real financial loss.

Telling a model to “be careful” is not a permission system. The model that interprets a request must not also be trusted to grant itself authority to execute it.

**Verigate is an independent authorization layer for AI-agent payments.** It separates understanding from authority: the AI interprets the request, deterministic Verigate policy decides whether the exact action is permitted, and the supported execution router enforces that permission before the transaction reaches the wallet.

The result is simple and important: **an AI agent can prepare a payment, but it cannot create its own permission to send it. The user remains in control of the wallet.**

## Why this control is necessary

Prompt instructions, model self-checks and AI-generated risk labels can influence what a model proposes. By themselves, they do not prove that a payment is authorized, bind approval to the exact transaction, or stop a modified action at the execution boundary.

Verigate makes authorization a separate, cryptographically verifiable step. Permission is based on explicit policy and user approval—not on the model's confidence or its claim that it followed instructions.

This matters to any platform that wants users to delegate payment preparation to AI without giving an agent unrestricted spending authority.

## How it works inside Anna

1. **The user describes a payment.** The request can be written in ordinary language.
2. **Anna interprets; it does not authorize.** Anna's host LLM extracts the recipient, amount, asset, network and context, asks for missing or ambiguous details, and provides advisory risk findings.
3. **Verigate makes the decision.** Its deterministic policy engine validates the payment fields and current authority state, including recipient/network validity, spending limits, first-recipient controls, review thresholds and rate limits. It returns a signed **ALLOW**, **WARN** or **BLOCK** decision.
4. **The user confirms.** Authorization requires a separate, explicit confirmation in the App. A WARN requires a distinct review of the exact matched warnings. BLOCK cannot be overridden. AI risk findings can make an otherwise eligible ALLOW stricter by escalating it to WARN; the model cannot create approval or lower a deterministic restriction.
5. **Verigate issues one-time authority.** A short-lived Ed25519 Execution Authorization is bound to the exact payment action: network, asset, recipient, amount, capability and policy context.
6. **The router enforces it.** Before wallet hand-off, Verigate ExecutionRouter verifies and consumes the permission. Replaying it or changing the authorized action causes rejection. The permission cannot be reused.
7. **The user signs in their wallet.** For native USDC on Base and Ethereum, the App can hand the exact authorized transaction to an injected EIP-1193 wallet provider when that provider is available in the Anna session. The wallet retains the private keys and asks the user to review and sign.

**Anna provides the natural-language runtime. Verigate provides the authority boundary. The user controls the wallet.**

## What makes Verigate different

- **Authority is outside the LLM.** The model cannot mint execution permission, approve its own proposal, or override a deterministic BLOCK.
- **Approval is bound to the exact action.** Recipient, asset, network and amount are not just displayed for review; they are part of the signed authorization.
- **Enforcement happens before the supported side effect.** The router verifies and consumes the one-time permission before handing the transaction to the wallet.
- **Replay and post-approval mutation are rejected.** A previous approval is not a reusable blank cheque.
- **Decisions are auditable.** The App verifies signed Ed25519 Decision Receipts. The wider Verigate protocol also provides a portable proof format and a standalone offline verifier.

This is not another wallet, another LLM, or a prompt-based safety filter. It is the control layer between an agent's proposal and an action with financial consequences.

## What is implemented

- Anna App with a bundled Verigate Python Executa.
- Natural-language payment interpretation through Anna host Sampling, with clarification for missing or ambiguous fields.
- Deterministic ALLOW / WARN / BLOCK policy decisions and signed Ed25519 Decision Receipts.
- Network-aware recipient validation.
- Per-transaction and rolling 24-hour authorization-budget controls, first-recipient limits, review thresholds and rate limits.
- Explicit user confirmation; separate exact-warning review for WARN.
- Short-lived, one-time Execution Authorization bound to the exact payment action.
- App-scoped confirmation gates and fail-closed ExecutionRouter consumption before wallet hand-off.
- Native USDC wallet hand-off path for Base and Ethereum, subject to EIP-1193 provider availability in the Anna session.
- Solana policy checks and signed authorization; Solana wallet transaction submission is not included in this App release.
- Public threat model, automated tests, CI workflows and local protocol demonstrations.
- Standalone offline verifier for the wider Verigate portable-proof format: `pip install verigate-verify`.

## Who needs it and why it can become a business

The first users are builders of AI-agent products that prepare payments or invoke privileged tools. The likely buyers are agent platforms, wallet and payment infrastructure providers, and companies that need delegated spending to remain bounded and auditable.

The commercial path is an integration SDK/API and paid implementation support for platforms that need policy enforcement, exact-action permissions and verifiable authorization records. A managed multi-tenant policy and evidence service is a later product step; it is **not shipped today**.

Anna is the first real user-facing integration. The underlying authority model is designed to serve other agent runtimes and execution adapters without making the LLM itself the security boundary.

## Current limitations

- App 0.1.28 is a Draft and is not Marketplace-published.
- Availability of an injected EIP-1193 wallet provider in a fresh Anna Cloud Agent session, and Cloud persistence across restart/reinstall, remain unverified.
- Native USDC wallet hand-off is limited to Base and Ethereum. Solana wallet submission is not included.
- The rolling 24-hour budget counts non-BLOCK authorization records, not chain-confirmed transfers. A cancelled or rejected wallet prompt does not automatically release the reserved budget.
- Accounting is scoped to one persistent Executa installation; separate Cloud Agent workspaces or issuer keys are not aggregated into one account-wide budget.
- The App gates the supported Verigate App/ExecutionRouter path. It is not a universal firewall for external wallets or actions that bypass that router.
- Verigate is not yet a hosted multi-tenant service. Production KMS/HSM custody and key-rotation operations are not shipped.
- The project has not undergone an independent third-party security audit.
- No successful signed or broadcast payment is claimed.
