# Details — paste into the public Build description

## AI can prepare the payment. It must not authorize itself to send it.

When an AI agent can move money, a wrong recipient, an altered amount, a prompt-injected instruction or a replayed approval can become a financial loss. Prompt rules and model self-checks may influence what an AI proposes, but they do not prove that a payment is authorized or enforce permission when the transaction is about to execute.

**Verigate is the independent authorization layer between an AI agent and a payment.** The model interprets the request; deterministic policy decides whether the exact action is permitted; the supported execution router enforces that decision before wallet hand-off. The agent never creates its own authority. The user remains in control of the wallet and its signing keys.

## How it works in Anna

1. **Interpret:** The user describes a payment in ordinary language. Anna's host LLM extracts recipient, amount, asset, network and context, asks for missing details, and provides advisory risk findings.
2. **Decide:** Verigate validates the exact payment and evaluates recipient/network validity, policy limits, first-recipient controls, review thresholds and rate limits. It returns a signed **ALLOW**, **WARN** or **BLOCK**. AI findings can escalate an eligible ALLOW to WARN; they cannot create approval or override BLOCK.
3. **Confirm:** The user explicitly confirms the exact payment in the App. WARN requires a separate review of the matched warnings. BLOCK is not overridable.
4. **Authorize:** Verigate issues a short-lived, one-time Ed25519 Execution Authorization bound to the exact action—network, asset, recipient, amount, capability and policy context.
5. **Enforce:** ExecutionRouter verifies and consumes the authorization before wallet hand-off. A replay or post-approval change to the authorized transaction is rejected.
6. **Sign:** For native USDC on Base and Ethereum, the App can pass the authorized transaction to an injected EIP-1193 wallet provider when one is available in the Anna session. The wallet retains the private keys and asks the user to sign.

Anna supplies the natural-language runtime. Verigate supplies the authority boundary.

## Why this is different

Verigate is not another wallet, chatbot or model-generated risk score. Authorization is a separate signed permission, bound to one exact action and checked at the execution boundary. This is the difference between asking an AI to behave and constraining what it is permitted to execute.

The wider Verigate protocol also includes portable authority evidence and a standalone offline verifier. This is distinct from proving that an Anna payment settled on-chain.

## Market and commercial path

Agent-platform developers, wallet/payment providers and enterprises need a way to delegate payment preparation without giving an AI unrestricted spending authority. Verigate is designed to provide spend controls, exact-action permissions and auditable evidence beneath those products.

Anna is the first user-facing integration. The near-term commercial path is SDK/API integration and paid implementation support; a managed multi-tenant policy and evidence service is a later step and is **not shipped today**.

## Current limitations

- App 0.1.28 remains a Draft and has not been approved or published in the Anna Marketplace.
- Wallet-provider availability and persistence in a fresh Anna Cloud Agent session remain unverified.
- Native USDC wallet hand-off is limited to Base and Ethereum; Solana wallet submission is not included.
- The rolling 24-hour budget counts non-BLOCK authorization records, not chain-confirmed transfers. A cancelled/rejected wallet prompt does not automatically release the reservation.
- Accounting is scoped to one persistent Executa installation, not aggregated across separate Cloud Agent workspaces or issuer keys.
- The App gates the supported Verigate App/ExecutionRouter path; it is not a universal wallet firewall.
- A hosted multi-tenant service, production KMS/HSM custody, key-rotation operations and an independent security audit are not shipped.
- No successful signed or broadcast payment is claimed.
