# Verigate Authority

## AI agents can request payments. They must not authorize themselves.

**An AI agent can misunderstand a request, follow malicious instructions or prepare a payment to the wrong address. When an agent is connected to a wallet, that mistake can become a financial loss. Verigate places an independent authorization layer between the AI and transaction execution.**

Verigate Authority is an authorization layer integrated into Anna. Anna's host AI interprets what the user wants to pay and provides contextual risk analysis, but it does not decide whether a payment is authorized. That decision belongs to Verigate's deterministic policy engine. The user remains in control of the wallet and its private keys.

## How it works

A user describes a payment in ordinary language.

Anna's host LLM identifies the recipient, amount, asset and network, asks for missing or ambiguous details, and provides a separate contextual risk review. If Anna Sampling is unavailable, the App can show a clearly labelled conservative policy-only preview; that fallback does not claim to have performed AI review and cannot issue execution authority.

Verigate validates the exact payment and evaluates it against deterministic policy rules. It checks the recipient for the selected network and applies transaction limits, first-recipient controls, review thresholds, rolling authorization-budget limits and rate limits. It returns a signed decision: **ALLOW, WARN or BLOCK**.

The AI is advisory. Its risk findings can make an otherwise eligible ALLOW stricter by escalating it to WARN. The model cannot create approval, lower a policy restriction or override BLOCK.

A fresh ALLOW can proceed through explicit user confirmation. A WARN requires a separate, one-time review of the exact matched warning rules, followed by a fresh policy and authority check. BLOCK cannot be overridden.

After the required confirmation, Verigate issues a short-lived, one-time Ed25519 Execution Authorization. It is cryptographically bound to the exact payment action, including the network, asset, recipient and amount.

Before wallet hand-off, Verigate ExecutionRouter verifies and consumes that authorization. A changed transaction, reused permission or failed/uncertain consumption is rejected or fails closed; the permission cannot be treated as reusable.

For native USDC on Base and Ethereum, the App can hand the authorized transaction to an injected EIP-1193 wallet provider when one is available in the Anna session. The wallet retains the private keys and asks the user to review and sign. Anna and Verigate do not custody the wallet keys.

**The AI interprets the request. Verigate enforces authority. The user controls the wallet.**

## Why this matters

Most AI safeguards ask a model to follow instructions, check its own answer or recognise suspicious prompts. That is not an authorization boundary. A model can make mistakes, be manipulated by prompt injection or prepare a different recipient or amount after the user has described the intended payment.

Verigate does not rely on the AI behaving correctly. It separates interpretation from permission, binds authorization to the exact action and checks that authorization at the supported execution boundary before wallet hand-off.

This is the difference between telling an AI to be careful and technically constraining what it is permitted to execute. The same authority model is intended for agent actions beyond payments, including privileged tools and business operations; the Anna App is its first user-facing payment integration.

## What is working today

- Anna App **0.1.28** with bundled production Verigate Executa **0.1.16**.
- Natural-language payment interpretation and contextual risk review through Anna's host LLM Sampling interface.
- Deterministic **ALLOW / WARN / BLOCK** decisions and Ed25519-signed Decision Receipts.
- Recipient-address validation for the selected network and checks for missing or ambiguous payment details.
- Per-transaction limits, first-authorization limits for new recipients, review thresholds, rolling 24-hour authorization-budget controls and rate limits.
- Explicit App-level user confirmation; WARN requires a separate review of the exact matched warnings.
- Short-lived, one-time Ed25519 Execution Authorizations bound to the exact payment action.
- ExecutionRouter verification and fail-closed, one-time permission consumption before wallet hand-off.
- Native USDC wallet hand-off path for **Base and Ethereum**, subject to EIP-1193 provider availability in the Anna session.
- Solana policy checks and signed authorization. Solana wallet transaction submission is not included in this Anna App release.
- Standalone offline verifier for Verigate's portable authority-proof format: `pip install verigate-verify`.
- **626 Python tests passed, 4 skipped**, and **61/61 Anna UI end-to-end tests passed**.
- Reproducible Executa build, packaging and extracted-package smoke tests passed for Windows x86_64, Linux x86_64, macOS ARM64 and macOS Intel x86_64.

## Current status and honest limitations

Anna App **0.1.28** is the current bundle. Its immutable package is ready, but its Anna platform status is **Draft**: it has not been submitted for review and is not Marketplace-published. It bundles production Executa **0.1.16**.

The latest main-branch CI run passed all three jobs: Anna UI, Python tests and contracts. The four-platform Executa workflow also passed its build and package smoke tests. These results demonstrate the tested source and build paths; they are not evidence of a published Marketplace app or a successful on-chain payment.

Live tests in the actual Anna Runtime were performed on immutable App versions **0.1.25** and **0.1.26**. They demonstrated Anna host-LLM interpretation, deterministic policy evaluation, signed Decision Receipt verification, one-time authorization, ExecutionRouter consumption and the MetaMask prompt for a 25 USDC Base transfer. The user cancelled at the wallet prompt because the test wallet was empty. **No wallet signature, transaction hash, broadcast or on-chain settlement occurred.** App 0.1.27 added wallet-state lifecycle hardening; App 0.1.28 carries that runtime forward and refreshes listing media.

The wallet hand-off depends on an EIP-1193 provider injected into the Anna session. Its availability in a fresh Cloud Agent session, and persistence across the supported Cloud Agent lifecycle, still need verification. Native USDC wallet submission is limited to Base and Ethereum; Solana policy checks do not mean Solana wallet submission is implemented.

The rolling 24-hour budget counts non-BLOCK authorization records, not chain-confirmed transfers. A cancelled or rejected wallet prompt does not automatically release the reserved budget. Accounting is scoped to one persistent Executa installation; separate Cloud Agent workspaces or issuer keys are not aggregated into one account-wide budget.

The App gates the supported Verigate App and ExecutionRouter path. It is not a universal firewall for every wallet or external client: actions that bypass that router are outside this App's enforcement boundary.

The project has not undergone an independent third-party security audit. A hosted multi-tenant service, production KMS/HSM custody and operational key-rotation service are not shipped.

## What comes next

The immediate next step is to complete Anna App review and verify the complete integration in a fresh Cloud Agent session, including wallet-provider availability and persistence.

We then need a controlled low-value payment test with independent chain observation. A wallet-returned transaction hash alone will not be treated as proof of settlement.

On the product side, the next priorities are cross-Agent budget accounting through a trusted platform principal and concurrency-safe shared ledger, published proof-format conformance vectors, an independent security review, and SDK/API integrations that let other agent platforms use the same authorization layer.

Our goal is straightforward: **AI agents should be able to act, but they should never be able to grant themselves permission to act.**
