# Verigate Authority

## An AI agent can request a payment. It should not be able to approve one.

The moment an AI agent can move money, a bad instruction can become a real loss. The agent might misunderstand the request, pick the wrong recipient or be manipulated into preparing a payment the user never intended.

Telling the model to be careful is not enough. The decision to spend money needs to sit outside the model.

**Verigate adds that independent check between an AI agent and the wallet.** It gives payment apps a way to set clear spending rules and enforce them before a transaction is handed to the wallet.

## How it works

Take a straightforward USDC payment. The agent works out the recipient, amount and network. Verigate checks the proposed payment against the rules: transaction limits, first-time recipient controls, review thresholds, rolling authorization budgets and rate limits.

The result is one of three decisions:

- **ALLOW** — the payment meets the rules and can proceed to user confirmation.
- **WARN** — the user must review the specific rule that was triggered and confirm again.
- **BLOCK** — the payment is rejected. The AI cannot talk its way around the decision.

The model can help understand the request and flag risks, but it does not grant permission. It can make a decision more restrictive; it cannot approve a blocked payment.

After the required user confirmation, Verigate creates a one-time cryptographic authorization for that payment. It is tied to the exact network, asset, recipient and amount. Before the wallet receives the transaction, the ExecutionRouter checks the authorization and consumes it. A changed payment or reused authorization is rejected.

The wallet keeps the private keys. The user remains in control of signing.

## Why build this

Most AI safety advice is still advice to the model: follow the instructions, check your work, do not make mistakes. That is not a reliable place to put control over money.

Verigate separates two jobs that should never belong to the same component: the AI works out what the user is asking for; a separate policy engine decides whether the resulting payment is allowed.

We are building Verigate for teams developing AI-agent platforms, wallets and payment products. Anna is the first application integration.

## What is working today

The Anna integration includes deterministic ALLOW / WARN / BLOCK decisions, signed Decision Receipts, one-time Ed25519 Execution Authorizations and ExecutionRouter checks before wallet hand-off. The current app supports the native USDC hand-off path for Base and Ethereum when an EIP-1193 wallet provider is available in the Anna session.

The automated suite reports **626 Python tests passed (4 skipped)** and **61/61 Anna UI end-to-end tests passed**. Executa build and package smoke tests have also passed on Windows, Linux and both supported macOS architectures.

There are important limits to be clear about. Anna App 0.1.28 is still in Draft and has not been published. Runtime testing on earlier immutable app versions reached the MetaMask confirmation prompt for a 25 USDC Base payment, but the test was cancelled before signing. **There has been no broadcast or completed on-chain payment.** Verigate protects the supported App and ExecutionRouter path; it is not a universal wallet firewall. A public third-party SDK/API and an independent security audit are not yet available.

## What comes next

The next steps are to complete the Anna review, verify wallet access in a fresh Cloud Agent session, and run a controlled low-value payment with independent on-chain confirmation. After that, the priority is making the authorization checks straightforward for other agent and wallet developers to integrate.
